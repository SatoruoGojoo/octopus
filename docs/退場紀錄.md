# Octopus 退場紀錄

> **本檔定位**：被砍掉的方案與砍掉的理由，存檔備查——**避免重蹈**，也避免有人（含未來的自己與 AI）好心把它們加回來。
> 這裡**不是**行為規格。現行行為一律以 [Octopus-功能文件.md](Octopus-功能文件.md) 為準。
> 想加回其中任何一項之前，請先讀該項的「退場原因」，並回答「這次有什麼不一樣」。

---

## 1. 定位演進（v0 → v0.6）

| 版本 | 定位 | 退場原因 |
|---|---|---|
| v0 | PM/FE/BE 多角色協作中樞（13~17 agent） | PM/FE 是不存在的使用者——服務的角色根本沒有人 |
| v0.x | 唯讀諮詢 → 完整 SDD 引擎 → 個人全棧+UI/UX 設計官（12 agent） | 範圍反覆膨脹；最終認清真實需求是**優化個人後端工作流** |
| v0.5 | 個人後端工作流，7 agent＋多執行模式 | 編制對了，但模式矩陣膨脹（見 §3） |
| **v0.6（現行）** | 個人後端工作流，7 agent 精實編制＋兩個停點 | — |

## 2. 退場的 agent 與角色

| 退場項 | 內容 | 退場原因 |
|---|---|---|
| **多角色協作中樞（v0）** | PM/FE/BE 各有入口；Feasibility 可行性卡片（六欄位）、Triage 前後端分流 agent、FE task 欄位規格、MSW mock 產出 | 服務不存在的使用者 |
| **全棧雙 Builder（v0.x）** | +UI 前端專家、Builder 拆 FE/BE、task 端別欄位確定性路由 | 定位收斂為後端專用 |
| **UI/UX 設計官（v0.x）** | 實作前出 design tokens/佈局，實作後「截圖→挑刺→修正」精緻度審查迴圈（上限 2~3 輪） | 同上 |
| **Guardian 治理 agent（v0.x）** | spec 狀態流轉的專職裁決者 | 狀態流轉是確定性動作，hooks + command 就能做——**code 能答的不用模型** |
| **Examiner 考官（v0.x）** | merge 前的認知債對齊——考 TPM 有沒有真的看懂 | 「理解 vs 盲簽」邊界改由 Builder 的**逐 task 隨行回報**承接：邊做邊懂，比事後考試便宜 |
| **環境／設定查詢 agent（提案，未實作）** | 專門回答「測試站/正式站是哪些」的 agent | 讀固定格式的檔案是 Read，不是判斷；agent 也得從某個檔讀，不會憑空多出資訊，只是多一次往返。**且 subagent 讀不到主對話 memory**——正解是寫進目標 repo 的 `CLAUDE.md`（每次對話與 subagent 都自動載入） |

**擴編路線（若未來部署到團隊共用）**：意圖漂移檢查官（比對客戶原話＝糾紛留痕）、合約對齊驗收官（範圍對齊＝請款驗收）、UAT 測試官（客戶驗收測試）獨立成編——專案公司情境約 11~13 agent。原則：**每多一條「對外部利害關係人的問責邊界」，才加回一個守邊界的 agent。**

## 3. 退場的模式與分支（v0.6 減法）

砍除判準：**新增分支前先答「刪掉它會壞什麼」**——答不出具體損失就不該存在。以下四項都答不出來。

### 3.1 `auto` 模式（v0.3~v0.5）

- **原本是什麼**：指令加 `auto` 跳過拍板 OK 停點，由 `/octopus:build` 入口自動鎖定（未定案決策卡取建議選項＋Arena 留痕「auto-locked」），純一條龍直達驗收。
- **退場原因**：它讓 `octopus.status: Locked` **帶兩種意思**——「TPM 拍板過」或「只是規格定稿、沒人看過」。設計文件與 build.md 都得靠旁註解釋這個差別，是最貴的一處複雜度。它省下的是 TPM 30 秒（而且 TPM 在管線起點本來就在場、剛答完 Analyst 反問），換來的是「方向全錯的整輪 build」風險。
- **連帶退場**：build 入口對 `Draft` change 的**自動鎖定旁路**。現行行為是停下請 TPM 拍板。
- **要加回來的前提**：先證明拍板停點真的是瓶頸（量測 TPM 在該點的等待時間），且能在不讓 `Locked` 多義的前提下實作（例如另設 `AutoLocked` 狀態——但那是多一個狀態換少一個模式，通常不划算）。

### 3.2 `step` 模式（v0.3~v0.5）

- **原本是什麼**：指令加 `step` 改為逐步確認——每條 task、每個步驟完成後停下呈現再續，執行中決策改為當場以決策卡請示。
- **退場原因**：它是自主模式的反向鏡像，等於整條管線要維護兩套流程語意（每個「不等人」的規則都要附一句「step 模式除外」）。而它存在的理由（想盯流程）已被**隨行回報**覆蓋：TPM 本來就會逐條看到 task 回報，看到不對勁隨時可以插話打斷。
- **要加回來的前提**：實際發生過「看到回報想喊停但來不及」的案例。

### 3.3 epic / roadmap（v0.4~v0.5）

- **原本是什麼**：Architect 自主判斷需求該拆成單 change 或多筆 change（＝epic），拆時另產 `openspec/roadmaps/<需求名>.md` 記各 change 名稱/順序/相依（roadmap 不是 change、不帶 `octopus.status`）；`/octopus:build` 收到 roadmap 則依相依順序逐 change 執行，前一筆經 TPM merge 後才啟動下一筆。連帶有「規劃輕問」——Analyst 釐清後問一句組織方式。
- **退場原因**：(1) `openspec/roadmaps/` 是自訂資料夾，`openspec validate --all` 的容忍度從未實測；(2) 沒有任何實際使用證據顯示「單 change 不夠」；(3) 它讓 Architect 多揹一個判斷、spec/build/main 三個 command 各多一條分支、使用指南多一個術語。需求大到裝不進一筆時，TPM 自己再跑一次 `/octopus:spec` 開第二筆就好——**拆分判斷交給人比讓它猜便宜**。
- **連帶退場**：規劃輕問。
- **要加回來的前提**：實際遇到一個需求，手動開多筆 change 時明顯感到「順序與相依記不住」。

### 3.4 管線內的 browser 驗證（v0.5）

- **原本是什麼**：tasks 每條標 `test`（預設）或 `browser`；`browser` 是 opt-in 建議，TPM 在拍板停點勾選才生效；build 步驟 4 由 Core（主對話）親自操作 Chrome＋截圖（subagent 用不到瀏覽器工具），結果附在驗收報告之後；環境不可用不中斷管線、報告標紅原因。
- **退場原因**：四個條件（tasks 標註、拍板勾選、Core 親自跑、環境降級處理）散在設計文件、spec.md、build.md、architect.md 四處，而它的實質內容只是「驗收前你自己開瀏覽器看一下」。同時它讓 tasks.md 多一個欄位、拍板停點多一個勾選動作。
- **現行替代**：Reviewer 在驗收報告的「高風險變更點」段落註明「建議親自在 <測試站/頁面> 確認 <什麼>」。真要 Claude 跑瀏覽器就明講——那是一次性請求，不是流程步驟。
- **要加回來的前提**：截圖驗證變成每筆交付都要做的事（而不是偶爾），且已有明確的通過/不通過判準（現行沒有判準，只留截圖）。

## 4. 退場的格式與基建

| 退場項 | 內容 | 退場原因 |
|---|---|---|
| **自有 spec 格式（v0.1~v0.4）** | `specs/NNN-*` ＋ frontmatter `status`；內建 EARS 範本 `templates/spec-template.md`、「範本跟著目標 repo 走」讓位規則 | 全面換血為 OpenSpec 格式——活文件＋change 生命週期原生支援「修復狀態追蹤」（code 已修、資料待補、未 archive＝留開），狀態機平移到 change 的 `.openspec.yaml` |
| **以「Arena 存在」為 hook 啟動條件（v0.3）** | plugin hook 只在專案有 `.claude/.octopus-arena/` 時生效（守門跟著專案走） | 實務證偽：init 是每個用 Octopus 的專案都會跑的起手式，該條件等於「用 Octopus＝全時被管」——日常合法操作（TPM 叫 Claude 在主幹 commit）也被攔。改為 run-marker：守門跟著**管線**走，不跟著專案走 |
| **`readFileSync(0)` 讀 hook stdin（v0.2）** | 同步讀取 PreToolUse payload | 同步阻塞 event loop 直到 EOF，harness 沒關 stdin 就永遠不返回，且 `setTimeout` 看門狗此時觸發不了——實測撞到 harness 的 hook timeout 上限。改為非同步讀＋5s 逾時 |
| **Arena 幽靈分片（v0.x 規劃，v0.8 除名）** | `architecture.md` / `conventions.md` / `glossary.md` 三個知識分片 | 從未被任何 command/agent 建立或讀寫（只存在於設計文件一行），且與 §6.1 原則自相矛盾——architecture/conventions 是可從 code 推導的事實，沉澱即腐爛。Arena 定位收斂為「私有工作區」三住戶：decisions（知識）／.run（狀態）／metrics（遙測） |
| **`/octopus:recall` 指令（P3 構想，未實作，v0.8 除名）** | 獨立的決策回憶指令 | 場景拆解後皆有歸屬：管線內回憶＝spec 前置讀取 Arena（Core 接線）、管線外追問＝Scout 讀 decisions.md（/octopus:ask）。獨立指令過不了 §1.4（刪掉無具體損失），且要使用者記得跑——違反「拍板後全自主」。通用記憶（codebase 事實、session context）明文交給平台（CLAUDE.md／auto-memory），Octopus 不自建記憶引擎 |

## 5. 退場的指令入口（v0.7 減法）

v0.6 的原則是「砍模式不砍指令」。v0.7 砍的是指令本身——判準相同（刪掉它會壞什麼），差別在於這次有**使用證據**而不只是設計推理。

### 5.1 `/octopus:quick`（v0.1~v0.6）

- **原本是什麼**：小修小補輕通道。適用性檢查（擋 schema/migration、對外 API 契約、權限認證、跨模組行為）→ 在 `quick/<slug>` branch 上實作＋測試 → 十行內簡版報告 → 不 commit。刻意不開 change，設計目的是「防止小事也被流程綁架」，在 §2.3 被列為設計支柱之一。
- **退場原因**：**實測從未被使用過**。TPM 的日常小修一律直接在主對話下指令，quick 的四道硬擋因此一次都沒生效——保護一條沒有人走的路徑，不是保護。它同時讓 Builder persona 揹一個第二輸入型態（「或直接的小修描述」）、讓驗收報告標題多一個分支、讓 run-marker 與 feature branch 規則各多列一個 command。
- **更根本的問題**：它的適用判準是**改動大小／風險**，而正確的分界線是**「spec 要不要變」**。純缺陷修正（code 沒做到 spec 本來就寫的事）修完 spec 一個字不用改，本來就不該進管線；而它擋下的那四類，幾乎必然伴隨 spec 變更。判準換掉之後，quick 這個中間層就沒有位置了。
- **連帶退場**：Builder 的 quick 輸入型態與 `quick/<slug>` branch 命名；§2.3 的「quick/main 雙通道」支柱改寫為「管線只服務需要 spec 的工作」。
- **代價（已知並接受）**：日常小修時無 run-marker，兩支 hook 都不生效——主幹保護在 Octopus 之外靠 TPM 自律。但這個代價在 quick 從未被使用時本來就已經存在，刪除只是讓它變得誠實。
- **要加回來的前提**：實際發生過「因為沒有輕通道而把小事硬塞進 main 管線」或「小修時誤推主幹」的案例。注意：加回來時判準應該是「spec 要不要變」，不是改動大小。

### 5.2 `/octopus:tasks`（v0.1~v0.6）

- **原本是什麼**：單獨產 tasklist 不實作。情境 A 給 change 名稱就展開；情境 B 給需求文字則先由 Analyst 輕量釐清（≤1 輪）再拆，輸出標註「非正式 tasklist」。
- **退場原因**：(1) `/octopus:spec` 的 Architect 第 7 步**本來就連 tasks 一起產**（理由：TPM 在拍板停點要一次看到完整包），所以「從 change 展開」幾乎永遠是在重新產生一份已經在硬碟上的檔案；(2) 「無 change 的需求文字 → 非正式 tasklist」這一支跟 tasklist 格式**本身矛盾**——格式規定每條要標 `（對應：Requirement <名稱>）`，沒有 change 就沒有 spec delta，這欄無從填起。追溯斷了的 tasklist 不是 SDD tasklist，只是待辦清單，直接在對話裡問就有。
- **連帶保留**：Architect 的 tasks 展開能力**必須留著**——`/octopus:build` 遇到手建的 change 缺 `tasks.md` 時要補產。但它從「情境 B」（一個與起草並列的模式）降為一個窄入口，tasklist 的格式規格獨立成節，供起草與補產共同引用。這修掉一個文件組織問題：原本 SDD 主線（情境 A）用一句「規則同情境 B」去引用支線，讀起來像主線依賴支線。
- **要加回來的前提**：實際遇到「想在拍板前先估量工作量、但不想產生 change」的需求，且頻率高到值得一個指令。
