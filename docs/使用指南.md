# Octopus 使用指南

> 給「用 Octopus 的人」（TPM）的操作手冊。這裡放的是**無法從 code 推導的 meta 操作知識**——遇到某情境該叫哪隻腳、術語是什麼意思。
> 設計原理與各腳的邊界，見 [Octopus-功能文件.md](Octopus-功能文件.md)；某個功能為什麼被砍掉，見 [退場紀錄.md](退場紀錄.md)。

## 情境 → 指令決策地圖

先問自己兩題，90% 的情況就定位了：

```
Q1. 我只是想「知道 / 查 / 審」，還是要「改東西」？
Q2. 如果要改：是小修補，還是一個正規需求？
```

### A. 只想知道 / 查 / 審（不改 code）

| 你的情境 | 用這個 | 誰接手 |
|---|---|---|
| 這段 code 誰寫的、為什麼這樣、進度到哪 | `/octopus:ask <問題>` | Scout |
| 想快速重建對整個專案的理解（分層、模組、關鍵流程） | `/octopus:overview [範圍]` | Scout |
| Schema 怎麼設計、三種 DB 方言差異、migration 影響、要不要加索引 | `/octopus:db <問題>` | DBA |
| 東西炸了 / 行為不對，要找根因（不只哪行炸，是為什麼炸） | `/octopus:debug <錯誤>` | Debugger |
| 想審一個 branch/PR 的品質，要一份可貼 PR 的驗收報告 | `/octopus:review [branch]` | Reviewer |

### B. 要改東西

| 你的情境 | 用這個 | 說明 |
|---|---|---|
| 純缺陷修正：**修完 spec 一個字都不用改**（code 沒做到它本來就該做的事） | 不進 Octopus——直接在對話中講就好 | 沒有 delta 可寫，開 change 只會產生空提案。代價：管線外沒有 hook 守門 |
| 正規需求（含 bug 修復要留追蹤），想**先想清楚再動**，可能改天才實作 | `/octopus:spec <需求>` | 產 OpenSpec change（Draft），你回 OK 後鎖成 Locked，之後再 build。一個需求一筆 change |
| change 已落檔，現在要實作到驗收 | `/octopus:build <change>` | 全自主，每條 task 隨行回報，帶驗收報告回來（change 還是 Draft 的話，入口會先停下請你拍板） |
| 需求清楚，想**一口氣從討論做到驗收** | `/octopus:main <需求>` | spec + build 連跑：拍板一個 OK 後全自主到驗收 |

### C. 特殊起手

| 你的情境 | 用這個 |
|---|---|
| 第一次把 Octopus 裝進一個既有專案 | `/octopus:init`（每專案跑一次；會檢查 OpenSpec CLI 與結構） |
| 需求很模糊 / 只有客戶訊息截圖，想先被挑戰、釐清 | 直接啟動 **analyst** agent（或跑 `/octopus:spec`，它第一步就是 analyst） |

**一句話記法**：`ask/overview/db/debug/review` 是**唯讀通道**（只問不改）；`spec→build`／`main` 是**正規交付**。**沒有中間檔**——不改變預期行為的小事直接在對話裡做，不進 Octopus。

## 術語對照表

| 術語 | 一句話解釋 |
|---|---|
| **TPM（你）** | 這顆頭。只做三件不可替代的事：**定義意圖、拍板取捨、驗收放行**，其餘交給七隻腳。 |
| **一顆頭 ＋ 七隻腳** | 頭＝你；七隻腳＝7 個專家 agent。Core 是頭的延伸，不佔腳。 |
| **七隻腳 / agent** | scout（考古＋鳥瞰）、analyst（需求）、architect（規格）、builder（實作）、reviewer（審查）、dba（資料庫）、debugger（除錯）。 |
| **Core** | 編排層＝commands ＋ 主對話，屬頭不佔腳。刻意**不設 agent 檔**——它負責流程調度，不守單一邊界。 |
| **SDD** | Spec-Driven Development：先寫規格對齊、再實作的交付管線（spec → build）。 |
| **OpenSpec** | v0.5 起採用的 spec 格式與 CLI（[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)）：`openspec/specs/<domain>/` 是「系統現況」活文件；每筆工作是 `openspec/changes/<name>/` 一筆 **change**。 |
| **change** | 一筆變更提案資料夾：proposal（為什麼＋範圍）＋ spec delta（行為變更，Requirement/Scenario 句式）＋ tasks ＋ `.openspec.yaml`（Octopus 狀態）。新功能、bug 修復、資料修補都各是一筆 change。 |
| **archive（結案）** | `openspec archive`：把 change 的 delta 合回主 spec、整夾歸檔。**merge ≠ archive**——merge 決定 code 進主幹；archive 才結案。tasks 沒做完（如「code 已修、舊資料待補」）可以先 merge、change 留開追蹤。 |
| **決策卡** | Architect 產出的取捨呈現（選項／代價／何時會後悔），讓你**一屏拍板**，而不是逼你讀長文。 |
| **change 狀態** | `Draft → Locked → Implemented`，記在 `.openspec.yaml` 的 `octopus.status`。只由 command 確定性改寫，agent 無權動。**`Locked` 只有一個意思：你拍板過了**（沒有自動鎖定的旁路）。Implemented＝已 merge；archive 後整夾歸檔＝終態。 |
| **task 回報（隨行回報）** | Builder 每做完一條 task 即時回報「做了什麼／code 導讀 file:line／自主決定／測試」。單向呈現不等你回覆——這是你**隨行理解每條 task 對應 code** 的機制，守住「理解 vs 盲簽」邊界。 |
| **兩個停點** | 整條管線只停兩次：**拍板 OK**（change 落檔後，回一個 `OK` 即放行）與**驗收 merge**（build 段尾，不 merge 即否決）。**沒有第三個停點，也沒有跳過任一個的模式**。其餘全自主、不中途等人。 |
| **守門（run-marker）** | 兩支 hook（主幹保護、change 狀態機）**只在管線執行中生效**：管線起跑寫 `.octopus-arena/.run`、收尾刪除（TTL 4h 兜底 crash 殘留）。日常叫 Claude 做的 git 操作零干預。 |
| **管線判準** | 進不進管線看**「spec 要不要變」**，不是改動大小：純缺陷修正（code 沒做到 spec 本來就寫的事）沒有 delta 可寫，不進管線；預期行為要變、或發現該行為從未寫進主 spec，才開 change。 |
| **諮詢通道** | `ask`／`overview`／`db`：唯讀問答，不進交付管線、不留檔。 |
| **Arena** | 目標 repo 的 `.claude/.octopus-arena/decisions.md`，追記歷次拍板決策的知識庫。**預設私有**（進 .gitignore）。 |
| **來源標註（誠實原則）** | 每個論斷標依據等級：**權威**（直接讀到）／**推導**（多處綜合）／**示意**（文件描述，以 code 為準）／**查無**（找不到就明說，不杜撰）。 |
| **merge 權** | 永遠在你手上。所有實作都在 feature branch，Octopus **不 commit 主幹、不 merge**；archive 也要你點頭。 |

## 走一次：從需求到驗收（worked example）

以下用一個小需求「**使用者註冊時，email 重複要擋下並回友善錯誤**」走完整條管線。實際對話文字會因需求不同，這裡是讓你先看見「你會在哪幾個點被要求做決定」。

### 0. 前置（一次性）

專案要先有 OpenSpec：裝 CLI＋跑過 `openspec init`（`/octopus:init` 會檢查並引導）。

### 1. 起手

```
/octopus:spec 使用者註冊時 email 重複要擋下，回友善錯誤而不是 500
```

### 2. Analyst 反問（釐清，≤3 問 × ≤2 輪）

> - email 重複判定要 case-insensitive 嗎（`A@x.com` = `a@x.com`）？
> - 已存在時回哪種狀態碼——409 Conflict 還是 422？
> - 軟刪除的帳號算不算「已存在」？

**你怎麼答才有用**：答「驗收怎麼算過」，不要答「我想要很好用」。例如「case-insensitive；回 409；軟刪除的**不**算重複，可重新註冊」。答不出來，代表需求本身還沒想清——這一步正好幫你逼出來。

接著 Analyst 會做**魔鬼代言人挑戰**（例如：「並發兩個相同 email 同時註冊，你的 application 層檢查擋得住嗎？」），挑戰結果一併呈現。

> 需求大到一筆 change 裝不下時，Architect 會照樣產出最合理的那一筆，並告訴你「這個需求含 N 個可獨立驗收的交付面，建議拆成 N 次 spec」——**拆不拆是你決定**，它不會自己拆。

### 3. Architect 產出完整包（change：proposal ＋ delta ＋ tasks ＋ 決策卡）

你會拿到 `openspec/changes/fix-signup-email-unique/`：
- `proposal.md`（目標與動機／範圍 In-Out／方法概述）
- `specs/auth/spec.md`（delta：`## ADDED Requirements`，Requirement＋可測 Scenario）
- `tasks.md`（逐條含相依與對應 Requirement）＋ `.openspec.yaml`（`octopus.status: Draft`）
- 一張**決策卡**，例如：

> **決策卡：重複檢查放哪一層**
> | 選項 | 做法 | 代價 | 何時會後悔 |
> |---|---|---|---|
> | A（建議） | Application 層先查 ＋ DB unique 索引兜底 | 兩處都要維護 | 幾乎不會 |
> | B | 只靠 DB unique constraint | 使用者只看到 500，訊息不友善 | 需要友善錯誤時 |
>
> **不可逆性**：可隨時改。

### 4.【拍板 OK 停點】

你一次看到完整包（proposal 摘要＋決策卡＋tasklist）。**回「OK」就好**——OK＝所有決策卡採建議選項＋同意鎖定（`octopus.status: Draft → Locked`，決策追記 Arena）；有個別意見才逐項回（例：「決策卡用 B，其他 OK」）。

> 想先放著改天再做？**不說 OK 就維持 Draft**，正常結束，之後隨時回來。直接跑 `/octopus:build` 也行——它會在入口停下來，把同樣的完整包呈給你拍板，**不會替你鎖定**。

### 5. 執行段（全自主，但看得到進度）

```
/octopus:build fix-signup-email-unique
```

Build 會自己跑：驗狀態（`Locked` 才動工）→ 開 feature branch → **Builder 逐 task 隨行回報**：每做完一條 task 你就收到一則回報（做了什麼／code 導讀／自主決定／測試），todo 進度條同步勾銷——**單向呈報，不等你回話**，看到不對勁隨時可以插話打斷 → Reviewer 審查 → **P1 自動退修（上限 3 輪）** → 帶**驗收報告**回來。

### 6.【唯一硬停點：驗收 merge】

你看驗收報告（開頭是執行中自動拍板清單；報告可直接當 PR description），滿意就**自己 merge**（或明確同意後由它代跑）；不滿意就不 merge——branch 上一切可逆，不 merge 即否決。merge 後 change 標 `Implemented`。

**接著是結案判斷（merge ≠ archive）**：
- tasks 全完成 → 它會建議跑 `openspec archive`（delta 合回主 spec＋歸檔），你點頭就結案
- 還有沒做完的 task（例如「補跑舊資料 backfill」）→ **change 留開**，這就是你的修復追蹤：`openspec list --changes` 隨時看得到「code 已修、資料待補」的狀態，補完再 archive

> 全程需要你的只有第 4 點的一個 OK、第 6 點的 merge 與 archive 點頭。**這兩個停點都不能跳過**——前者擋掉方向全錯的整輪 build，後者是你的合併權本身。

## 卡點排解

| 症狀 | 怎麼辦 |
|---|---|
| **spec/build 在入口就停，說缺 `openspec` CLI 或結構** | v0.5 起 OpenSpec 是前置依賴。照官方 README 裝 CLI（github.com/Fission-AI/OpenSpec），專案沒有 `openspec/` 就自己跑一次 `openspec init`（互動式），完成後回覆繼續。 |
| **`build` 在入口停下來/拒絕** | `Draft` 會**停下請你拍板**（不是拒絕——回 OK 就續跑）。真正會擋的是：`Implemented`（已 merge——剩餘 task 屬結案追蹤，要再動 code 請開新 change）、已 archive（已結案）、缺 `octopus.status`（跑 `/octopus:init` 補登或親手標註）。這些拒絕**刻意不可繞**。 |
| **決策卡跳出來，我不知道怎麼判** | 先看**「不可逆性」**欄：可隨時改的，選建議項（A）先跑，錯了再改成本低；標「基本不可逆」的才需要慎重。真的不確定就選 A（Architect 已附理由），或請 `analyst`／`db` 補一個角度再決定。 |
| **Analyst 反問我，我答不出來** | 那不是它刁難，是需求真的還沒收斂。用「**驗收怎麼算過**」的句式回（可測條件），答不出的那幾條就是你需要先想清楚的地方。 |
| **build 一直丟 task 回報給我，要不要回？** | 不用回，那是單向進度呈報（也是你隨行看懂 code 的機會）。看到方向不對就直接插話打斷；不出聲它就照 tasks 跑到底。 |
| **`build` 跑到一半停下來等我** | 不該發生——高風險決策、P1 三輪修不乾淨、spec 矛盾都是「保守預設＋留痕＋驗收報告集中呈報」（P1 修不乾淨會直接收尾、報告標紅）。真的中途停下就是它沒照規則走，直接說。 |
| **我想盯每一步、不要全自主** | 逐 task 回報就是給你盯的：每條做完你都會即時收到回報（含 code 導讀）。看到方向不對就直接插話打斷——不用等它問你。 |
| **要在頁面上實際點一遍才安心** | 管線不代跑瀏覽器。驗收報告的「高風險變更點」會列出建議親自確認的項目；想讓 Claude 跑就在驗收後直接說（例：「幫我開測試站看一下匯出」），那是一次性請求。 |
| **bug 修完了但舊資料還沒補，怎麼記？** | 這正是 change 生命週期的用法：merge code 後**不要 archive**，讓 change 留開（tasks 剩「補資料」那條沒勾）。補完資料、勾掉 task，再請它跑 `openspec archive` 結案。 |
| **Octopus 會不會自己 merge、動我主幹？** | 不會。所有實作都在 feature branch，它**不 commit 主幹、不 merge**；`openspec archive` 也要你點頭才跑。merge 權永遠在你手上。 |
| **我同意 merge 了，卻跳出「branch-guard 擋下 git merge／OCTOPUS_TPM_OK=1」** | 罕見：管線收尾（呈驗收報告）時守門已解除，之後的 merge 不會被攔。還撞到多半是管線 crash 殘留 marker（最多 4 小時自動失效，也可親手刪 `.claude/.octopus-arena/.run`）。被攔時 Claude 會直接用 `OCTOPUS_TPM_OK=1 git merge ...` 重跑（前綴＝你的同意留痕）；或你自己在終端機 merge——hook 只攔 Claude 的工具呼叫，不攔你。 |
| **平常請 Claude commit/push/merge 會被 Octopus 攔嗎？** | 不會。守門跟著管線走：只有 spec/build/main 執行中才生效，日常工作 hook 零干預。反過來說也成立——**管線外做小修時沒有主幹保護**，那段靠你自己。 |
| **可以直接用 OpenSpec 自己的 `/opsx:*` 指令嗎？** | 查詢類（status/list/show/view）隨意。會動檔案的（propose/apply/archive）建議走 `/octopus:*`——feature branch 紀律、拍板停點、狀態機、守門只在 Octopus 管線內有保障，混用會讓 change 缺 Locked/Implemented 紀錄（狀態漂移）。 |
| **需求很模糊、只有一張客戶截圖** | 別急著開 change。先把截圖丟給 `analyst`（或直接 `/octopus:spec`，它第一步就是 analyst），讓它先嗆你幾題釐清。 |
