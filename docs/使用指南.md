# Octopus 使用指南

> 給「用 Octopus 的人」（TPM）的操作手冊。這裡放的是**無法從 code 推導的 meta 操作知識**——遇到某情境該叫哪隻腳、術語是什麼意思。
> 設計原理與各腳的邊界，見 [Octopus-功能文件.md](Octopus-功能文件.md)。

## 情境 → 指令決策地圖

先問自己兩題，90% 的情況就定位了：

```
Q1. 我只是想「知道 / 查 / 審」，還是要「改東西」？
Q2. 如果要改：是小修補，還是一個正規需求？
```

### A. 只想知道 / 查 / 審（不改 code）

| 你的情境 | 用這個 | 誰接手 |
|---|---|---|
| 這段 code 誰寫的、為什麼這樣、架構分幾層、進度到哪 | `/octopus:ask <問題>` | Scout |
| Schema 怎麼設計、三種 DB 方言差異、migration 影響、要不要加索引 | `/octopus:db <問題>` | DBA |
| 東西炸了 / 行為不對，要找根因（不只哪行炸，是為什麼炸） | `/octopus:debug <錯誤>` | Debugger |
| 想審一個 branch/PR 的品質，要一份可貼 PR 的驗收報告 | `/octopus:review [branch]` | Reviewer |

### B. 要改東西

| 你的情境 | 用這個 | 說明 |
|---|---|---|
| 小修補：**單檔可定位、不碰 schema/契約/權限** | `/octopus:quick <任務>` | 輕通道，不留 spec，直接在 feature branch 做完 |
| 正規需求，想**先想清楚再動、要留 spec**，可能改天才實作 | `/octopus:spec <需求>` | 停在 Locked，之後再 build |
| spec 已經 **Locked**，現在要實作到驗收 | `/octopus:build <spec>` | 全自主，帶驗收報告回來 |
| 需求清楚，想**一口氣從討論做到驗收** | `/octopus:main <需求>` | spec + build 連跑，只停拍板一次 |

### C. 特殊起手

| 你的情境 | 用這個 |
|---|---|
| 第一次把 Octopus 裝進一個既有專案 | `/octopus:init`（每專案跑一次） |
| 需求很模糊 / 只有客戶訊息截圖，想先被挑戰、釐清 | 直接啟動 **analyst** agent（或跑 `/octopus:spec`，它第一步就是 analyst） |
| 只想要一份 tasklist、不要實作 | `/octopus:tasks <spec 或需求>` |

**一句話記法**：`ask/db/debug/review` 是**唯讀四腳**（只問不改）；`quick` 是**小改**；`spec→build`／`main` 是**正規交付**。

## 術語對照表

| 術語 | 一句話解釋 |
|---|---|
| **TPM（你）** | 這顆頭。只做三件不可替代的事：**定義意圖、拍板取捨、驗收放行**，其餘交給八隻腳。 |
| **一顆頭 ＋ 八隻腳** | 頭＝你；八隻腳＝7 個專家 agent ＋ Core 編排層。 |
| **八隻腳 / agent** | scout（考古）、analyst（需求）、architect（規格）、builder（實作）、reviewer（審查）、dba（資料庫）、debugger（除錯），加上 **Core**。 |
| **Core** | 編排層＝commands ＋ 主對話。刻意**不設 agent 檔**——它負責流程調度，不守單一邊界。 |
| **SDD** | Spec-Driven Development：先寫規格對齊、再實作的交付管線（spec → build）。 |
| **EARS** | 行為規格句式：`WHEN/WHILE/IF … THE SYSTEM SHALL …`。每條行為都要能對應一條**可測**驗收。 |
| **決策卡** | Architect 產出的取捨呈現（選項／代價／何時會後悔），讓你**一屏拍板**，而不是逼你讀長文。 |
| **spec 狀態** | `Draft → Locked → Implemented`。只由 command 在**你明確確認後**改寫，agent 無權動。 |
| **硬停點** | 整條管線只有兩個必停的點：①**拍板鎖定**（spec 段尾）、②**驗收 merge**（build 段尾）。其餘全自主。 |
| **輕通道（quick）** | 繞過完整管線的小修補入口——單檔、不碰 schema/契約/權限才走這條。 |
| **諮詢通道** | `ask`／`db`：唯讀問答，不進交付管線、不留 spec。 |
| **Arena** | 目標 repo 的 `.claude/.octopus-arena/decisions.md`，追記歷次拍板決策的知識庫。**預設私有**（進 .gitignore）。 |
| **來源標註（誠實原則）** | 每個論斷標依據等級：**權威**（直接讀到）／**推導**（多處綜合）／**示意**（文件描述，以 code 為準）／**查無**（找不到就明說，不杜撰）。 |
| **merge 權** | 永遠在你手上。所有實作都在 feature branch，Octopus **不 commit 主幹、不 merge**。 |

## 走一次：從需求到驗收（worked example）

以下用一個小需求「**使用者註冊時，email 重複要擋下並回友善錯誤**」走完整條管線。實際對話文字會因需求不同，這裡是讓你先看見「你會在哪幾個點被要求做決定」。

### 1. 起手

```
/octopus:spec 使用者註冊時 email 重複要擋下，回友善錯誤而不是 500
```

### 2. Analyst 反問（釐清，≤3 問 × ≤2 輪）

> - email 重複判定要 case-insensitive 嗎（`A@x.com` = `a@x.com`）？
> - 已存在時回哪種狀態碼——409 Conflict 還是 422？
> - 軟刪除的帳號算不算「已存在」？

**你怎麼答才有用**：答「驗收怎麼算過」，不要答「我想要很好用」。例如「case-insensitive；回 409；軟刪除的**不**算重複，可重新註冊」。答不出來，代表需求本身還沒想清——這一步正好幫你逼出來。

接著 Analyst 會做**魔鬼代言人挑戰**（例如：「並發兩個相同 email 同時註冊，你的 application 層檢查擋得住嗎？」），挑戰結果一併呈現。

### 3. Architect 產出完整包（spec ＋ tasks ＋ 決策卡）

你會拿到：
- `specs/012-signup-email-unique/spec.md`（`status: Draft`，EARS 行為規格 ＋ 可測驗收）
- `specs/012-signup-email-unique/tasks.md`
- 一張**決策卡**，例如：

> **決策卡：重複檢查放哪一層**
> | 選項 | 做法 | 代價 | 何時會後悔 |
> |---|---|---|---|
> | A（建議） | Application 層先查 ＋ DB unique 索引兜底 | 兩處都要維護 | 幾乎不會 |
> | B | 只靠 DB unique constraint | 使用者只看到 500，訊息不友善 | 需要友善錯誤時 |
>
> **不可逆性**：可隨時改。

### 4.【硬停點一：拍板鎖定】

你一次看到完整包，做兩件事：
1. **拍板決策卡**：說「用 A」→ 結論寫進 spec 的「已拍板決策」表。
2. **鎖定**：說「鎖定」→ `status: Draft → Locked`，決策追記 Arena。

> 想先放著改天再做？**不說鎖就維持 Draft**，正常結束，之後隨時回來。

### 5. 執行段（全自主）

```
/octopus:build specs/012-signup-email-unique/spec.md
```

Build 會自己跑：驗狀態是 Locked ✓ → 開 feature branch → 照 tasks 實作＋測試 → Reviewer 審查 → **P1 問題自動退修到乾淨（上限 3 輪）** → 帶**驗收報告**回來。這段你不用盯（除非它撞到例外停點，見下）。

### 6.【硬停點二：驗收 merge】

你看驗收報告（可直接當 PR description），滿意就**自己 merge**。merge 後這份 spec 標 `Implemented`。

> **全程只有第 4、6 兩個點需要你**。中間的釐清在前段一次講完，實作段預設不打斷你。

## 卡點排解

| 症狀 | 怎麼辦 |
|---|---|
| **`build` 說「狀態非 Locked，拒絕」** | 這道閘門**刻意不可繞**。回去跑 `/octopus:spec` 把 spec 拍板鎖定；已有 Draft spec 就確認後鎖。沒有「先做做看」的繞道。 |
| **決策卡跳出來，我不知道怎麼判** | 先看**「不可逆性」**欄：可隨時改的，選建議項（A）先跑，錯了再改成本低；標「基本不可逆」的才需要慎重。真的不確定就選 A（Architect 已附理由），或請 `analyst`／`db` 補一個角度再決定。 |
| **Analyst 反問我，我答不出來** | 那不是它刁難，是需求真的還沒收斂。用「**驗收怎麼算過**」的句式回（可測條件），答不出的那幾條就是你需要先想清楚的地方。 |
| **`build` 跑到一半停下來** | 只有三種例外會停：①**高風險決策**（migration／權限／對外契約／不可逆且 spec 沒涵蓋）——它會問你；②**P1 三輪修不乾淨**——需要你看它卡在哪；③**實作中發現 spec 矛盾**——回去補 spec。照它給的說明處理即可。 |
| **我想盯每一步、不要全自主** | 指令加 `step`（例：`/octopus:build ... step`）改成逐步確認模式。 |
| **Octopus 會不會自己 merge、動我主幹？** | 不會。所有實作都在 feature branch，它**不 commit 主幹、不 merge**。merge 權永遠在你手上。 |
| **需求很模糊、只有一張客戶截圖** | 別急著開 spec。先把截圖丟給 `analyst`（或直接 `/octopus:spec`，它第一步就是 analyst），讓它先嗆你幾題釐清。 |
